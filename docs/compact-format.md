# Минимальный пакет для LLM

Команды выполняются из корня `audit-agent`. [Вернуться в README](../README.md).

После успешного `stop` заберите **`llm.json`**. Вместе с ним передавайте краткое
описание проблемы, цель упражнения и результат валидации. Полный JSONL,
manifest, таблицу ссылок и статистику в обычный запрос добавлять не нужно.
Инструкция для разбора находится в [llm-analysis-prompt.md](prompts/llm-analysis-prompt.md).
Сжатие детерминированное: для подготовки пакета LLM не вызывается.

- Start, finish, exec и связанные файловые/сетевые операции объединяются в одну
  введённую команду. Сессия, tty и обычный cwd вынесены в общую таблицу `actors`.
  Время относительно начала, короткие ключи, UTF-8 без Unicode escapes.
- Повторные пользовательские команды остаются отдельными действиями, даже с
  одинаковым кодом завершения: вывод между повторами мог отличаться.
- Однотипные соседние операции внутри действия заменяются счётчиком `n`.
  Повторяющий введённую строку exec не дублируется; раскрытые alias/аргументы
  дочерних программ сохраняются в `exec`.
- Связь определяется PID, PPID, login/session и интервалом Bash-команды;
  это best effort. Только подтверждённые Bash-команды идут в `actions`.
  Неопределённые exec/операции идут в отдельный массив `context` с теми же
  короткими ID и ссылками на полный журнал. Это не подтверждённые действия
  пользователя; модель не должна оценивать их как его шаги или ошибки.
  `coverage.user_commands` показывает число подтверждённых команд. При отсутствии
  Bash hook массив действий может быть пустым: аудит сохранён в context, но
  авторство ввода не установлено. Дочерний exec в строке команды — не отдельная
  команда пользователя.
  Случайное соседство по времени не считается доказательством связи.
- По умолчанию на действие оставляются до 24 групп операций и 12 групп
  дополнительных exec. Приоритет у отрицательных syscall returns и операций
  изменения. Порядок оставшихся операций сохраняется. Счётчики `effects_omitted`,
  `exec_omitted` и `coverage.omitted_details` явно показывают сокращение деталей.
  **Сами введённые команды не обрезаются.** В полном снимке остаются все
  экспортированные события; ссылки есть и на сокращённые детали.
- Служебные границы, операции сборщика, успешные открытия `/dev/null`/`/dev/tty`
  и обычные auth-события убираются; ошибки открытий, AVC/SECCOMP/ANOM,
  пользовательские отметки и сведения о потерях остаются.
  Подготовка SSH-входа до первой подтверждённой команды, транспортные операции
  sshd и отдельное SSH-подключение для управления сборщиком тоже исключаются.
  Вручную введённый пользователем `run-parts` сохраняется. Счётчики исключённых
  событий находятся в статистике; полный JSONL не меняется.
- Известные шаблоны секретов (`--password`, `--token`, `API_KEY=`, Bearer,
  пароль в HTTP URL) заменяются на `<secret>`. Это ограниченная очистка;
  произвольное содержимое команд может по-прежнему содержать секреты.

Например, строки массива `actions`:

```json
[{"id":1,"t":2.4,"s":1,"cmd":"curl http://localhost","rc":7,"dt":0.1},{"id":2,"t":8.1,"s":1,"cmd":"systemctl restart nginx","rc":0,"dt":0.3}]
```

`s` — ID записи `actors`; `t` и `dt` — секунды, `rc` — реальный Bash `$?`.
`rc: null` означает отсутствие результата, а не успех. Статус pipeline относится
к Bash-команде целиком. `exec_sysrc`/`sysrc` — результат системного вызова;
например, connect `-115` может означать асинхронное подключение.
Успешное открытие файла на запись не доказывает изменение содержимого.

Пересобрать пакет закрытого окна с другими лимитами:

```bash
sudo incident-audit compact --session-id attempt-001
# Увеличить лимиты для подробного разбора:
sudo incident-audit compact --session-id attempt-001 --effects-limit 10000 --exec-limit 10000
# Жёсткая проверка бюджета в байтах; превышение — ошибка, команды не отбрасываются:
sudo incident-audit compact --session-id attempt-001 --max-bytes 32000
```

Для минимального пакета можно задать `--effects-limit 0 --exec-limit 0`;
это удалит детали операций и раскрытия exec, что снизит качество разбора.
`--max-bytes` проверяет размер JSON, **не** число токенов. При ошибке существующий
пакет не заменяется. Для очень длинной истории потребуется отдельное разбиение
анализа; скрытого усечения до бюджета нет.

Сжатие можно выполнять на сервере проверки, без auditd и root:

```bash
# Рядом нужны actions.jsonl и соответствующий actions.manifest.json.
incident-audit compact-file --input ./actions.jsonl --output ./llm.json
```

`llm.sources.json` связывает короткие ID действий с полными `event_id`.
Если разбор требует подробностей, выберите нужные события локально по этим ID
и подготовьте отдельный запрос. Таблица ссылок по умолчанию модели не нужна.

В `llm.stats.json` измерены байты до/после. Для токенов нужно использовать
токенизатор выбранной модели: соотношение байтов и токенов непостоянно.
В Go-экспорте `token_counts` остаётся `null`: бюджет проверяется по байтам,
а фактический расход полного запроса берётся из API `usage`. Прежняя
необязательная интеграция с Python-пакетом `tokenizers` удалена вместе с Python.

Исторический замер до отделения context: 50 событий полного снимка → 21 строка
(включая 6 Bash-команд, внешние exec и операции без уверенной привязки).
Размер 44 020 → 4 221 байт; 16 650 → 1 696 токенов по официальному
`deepseek_v4_tokenizer/tokenizer.json` из
[пакета DeepSeek](https://api-docs.deepseek.com/quick_start/token_usage/).
SHA256 токенизатора: `89085f12ef79460ac5f66d1119325ddfc694b4ab209d80bbd81d35f081dc9614`.
Это собственное тестовое окно сборщика, а не пользовательская попытка;
сокращения деталей по лимитам в нём не было. Для других историй доля экономии
будет отличаться. Измерение не включает обвязку API и ответ модели.

Вывод команд и содержимое файлов сейчас не собираются. `coverage.stdout` и
`coverage.file_contents` явно равны `false`: модель не должна выдумывать,
что показал `curl`, что было в конфигурации и почему решение прошло проверку.
Для такого анализа понадобятся отдельные ограниченные выводы/снимки и результат
валидатора. Формат уже оставляет эти ограничения видимыми.
