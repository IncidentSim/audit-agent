# Audit Agent

Самостоятельная утилита для сбора действий пользователя через Linux Audit и
подготовки компактного JSON для анализа LLM. Полный JSONL сохраняется отдельно.
Весь каталог можно скопировать на другую
машину или вынести в отдельный репозиторий. Установка работает через обычный
SSH либо локально внутри целевой VM. Зависимостей от Firecracker, Telegram,
vmctl и расположения соседних проектов нет.

## Требования

| Где | Что требуется |
| --- | --- |
| Целевая машина | Ubuntu/Debian, Linux x86_64, работающий systemd, Python 3.10+ |
| Ядро целевой машины | Linux Audit: `CONFIG_AUDIT` и `CONFIG_AUDITSYSCALL` |
| Права на целевой машине | root или sudo |
| Установка пакетов | Доступ к APT; установщик ставит `auditd` и `python3-audit` |
| Машина для удалённой установки | Python 3.10+ и OpenSSH client; подходит Linux, macOS или Windows |

Проверенная целевая ОС — Ubuntu 24.04, audit packages 3.1.2.
Другие дистрибутивы, ARM и контейнеры без доступа к kernel audit не заявлены.
Установщик проверяет платформу, systemd и доступность audit до настройки.
При immutable audit policy или правиле `never,task` он останавливается с
объяснением; существующую политику нужно предварительно привести в совместимое
состояние. Повторная установка сохраняет журналы и идентификатор машины.

## Установка одной командой по SSH

Из этого каталога на машине, с которой доступна целевая VM:

```bash
python3 deploy.py admin@vm.example.com --sudo --vm-id training-01 --verify
```

`--sudo` использует `sudo -n`: на целевой машине нужен sudo без запроса пароля.
Для root SSH этот флаг не нужен:

```bash
python3 deploy.py root@vm.example.com --vm-id training-01 --verify
```

Параметр `--vm-id` необязателен. Если он не задан, уникальный ID создаётся при
первой установке и сохраняется для повторных запусков. При необходимости можно
передать ID учебной сессии из любого оркестратора.

Дополнительные параметры:

```bash
python3 deploy.py admin@vm.example.com --sudo \
  --identity ~/.ssh/id_ed25519 --port 2222 \
  --ssh-option ProxyJump=bastion.example.com --verify
```

Можно использовать alias из `~/.ssh/config` вместо `admin@vm.example.com`.
Используется аутентификация SSH по ключу/агенту; пароль не читается.
Новые SSH host keys принимаются, изменившиеся отклоняются.
На целевой машине должен существовать `/usr/bin/python3`; другой путь задаётся
через `--python`. Если Python отсутствует, сначала установите его средствами ОС.

`deploy.py` собирает только файлы утилиты в архив, передаёт по stdin SSH,
распаковывает во временный каталог и вызывает установщик. Ключи, журналы,
локальные конфигурации и `__pycache__` в архив не входят. Временный каталог
после выполнения удаляется. `--verify` запускает тесты и реальные пробные действия.

## Локальная установка или перенос архивом

Скопируйте весь каталог на целевую машину и выполните там:

```bash
cd audit-agent
sudo python3 install.py --vm-id training-01
sudo python3 scripts/verify.py
```

Для переноса одним файлом на машине-источнике:

```bash
python3 deploy.py --bundle-only dist/audit-agent.tar.gz
scp dist/audit-agent.tar.gz admin@vm.example.com:/tmp/
```

В архиве файлы лежат без внешнего каталога. На целевой машине:

```bash
mkdir audit-agent
tar -xzf /tmp/audit-agent.tar.gz -C audit-agent
cd audit-agent
sudo python3 install.py --vm-id training-01
```

При создании архива укажите свободное имя: существующий файл не перезаписывается.
`--skip-packages` доступен у обоих установщиков, если зависимости уже подготовлены.

├── tests/                    # автоматические тесты

├── docs/
│   ├── llm.md                # подключение и вызов LLM
│   ├── compact-format.md     # формат, сжатие, лимиты токенов
│   └── prompts/              # инструкции для модели

├── analysis/                 # локальные результаты, вне Git

Все команды в документации выполняются из корня `audit-agent`.
Установленные команды `incident-audit start/stop/compact` сохраняют свои имена.

Логи остаются на диске целевой машины и исчезнут при удалении её диска.

## Что сохраняется

- Auditd: `execve/execveat`, смена каталога, открытия файлов на запись,
  создание/удаление/переименование, изменение прав/владельца/атрибутов,
  `connect`, события входа/выхода из SSH. Есть правила b64 и b32.
- Фильтр `auid!=unset` учитывает root SSH и сохраняет login UID при sudo.
  Системные демоны без login UID не попадают под syscall-правила.
- Для интерактивного **root Bash** добавлен hook: PS0 записывает введённую
  команду перед исполнением, PROMPT_COMMAND — её завершение и `$?`.
  Поэтому фиксируются `cd`, `echo`, pipelines, команды с ведущими пробелами,
  повторы и ввод `exit`. У `exit` обычно нет отдельного finish-события.
- Поддержаны многострочные команды, Unicode, декодирование hex,
  сборка длинных аргументов из нескольких audit records.

Для уже открытого терминала подключите hook вручную:

```bash
source /etc/profile.d/incidentsim-audit.sh
```

Новые интерактивные root Bash-сессии подключают его автоматически. Hook не
пишет историю непривилегированных shell: каталог журналов доступен только root.
Сам auditd отслеживает syscall-события всех login UID.

## Контракт для внешних систем: начало и конец работы

После установки учебная запись выключена. Внешние системы задают окно записи
явно; первый вход по SSH и первая команда автоматически его не открывают.
Для каждой попытки используйте отдельный ID сессии, например UUID.

**Система подготовки инфраструктуры** вызывает команду после полной подготовки
и внесения инцидента, до отправки пользователю ссылки:

```bash
sudo incident-audit start --session-id attempt-001
```

После успешного завершения (exit code 0) можно отправлять ссылку пользователю.
Команда возвращает JSON со `session_id`, `phase: "recording"`, `started_at`
и `start_boundary`. Это граница предоставленного пользователю рабочего окна,
а не утверждение, что он сразу ввёл первую команду.

**Система валидации** сначала закрывает то же окно, затем запускает саму проверку:

```bash
sudo incident-audit stop --session-id attempt-001
# Только после успешного stop запускать playbook/скрипт валидации.
```

`stop` фиксирует конец окна, дожидается обработки очереди auditd и автоматически
формирует `actions.jsonl`, `actions.manifest.json` и компактный `llm.json`
только для этой сессии.
Ответ — JSON; поля `output` и `manifest` содержат абсолютные пути к файлам,
`llm` — путь к пакету для модели, `events` — количество полных событий,
`llm_actions` — число действий в компактном пакете, `phase` — `stopped`.
Команда может выполняться несколько секунд: нужно дождаться её результата.
При ненулевом exit code сначала устраните ошибку и повторите stop; валидацию
до успешного закрытия окна не запускайте.

Пример сокращённого ответа stop:

```json
{"session_id":"attempt-001","phase":"stopped","output":"/var/log/incidentsim/sessions/attempt-001/actions.jsonl","manifest":"/var/log/incidentsim/sessions/attempt-001/actions.manifest.json","llm":"/var/log/incidentsim/sessions/attempt-001/llm.json","events":75,"llm_actions":12}
```

Обе команды запускаются внутри VM от root, в том числе через SSH с `sudo -n`.
ID: 1–96 латинских букв, цифр, `.`, `_`, `-`; первый символ — буква или цифра.

- Повторный start активной сессии с тем же ID возвращает исходное начало.
- Повторный stop закрытой сессии возвращает исходные файлы и конец окна.
- Если уже открыта другая попытка, stop старой сессии возвращает ошибку,
  чтобы задержавшийся запрос не разрешил запуск валидатора внутри нового окна.
- Другой ID не может закрыть текущую запись. Две записи одновременно запрещены.
- Закрытый ID не используется повторно. Для продолжения после неуспешной
  проверки создайте новую попытку с новым ID.
- После сбоя экспорта повторный stop сохраняет исходный cutoff и повторяет
  формирование файлов. Состояние хранится на диске.
- Перезапуск dispatcher в той же загрузке VM сохраняет окно. Перезагрузка
  самой VM требует отдельного восстановления и не смешивается с прежним окном.

Системный auditd остаётся работать и пишет исходный системный журнал. Учебный
JSONL записывается только внутри открытого окна. В границы audit-событий входят
номера kernel audit events: события в одной миллисекунде различаются по serial.
Буферизованные события перед stop учитываются при завершении. Команды валидатора,
выполненные после успешного stop, в учебный экспорт не входят.

Внутри окна не запускайте посторонние административные работы: по выбранному
контракту события между границами относятся к работе пользователя. Автоматического
различения человека и другой системы с тем же root-доступом нет.

## Файлы внутри VM

| Путь | Назначение |
| --- | --- |
| `/var/log/audit/audit.log` и ротации | Исходные audit records |
| `/var/log/incidentsim/sessions/ID/events.jsonl` и ротации | Учебные события открытого окна |
| `/var/log/incidentsim/sessions/ID/actions.jsonl` | Полный отсортированный снимок, автоматически создаваемый stop |
| `/var/log/incidentsim/sessions/ID/actions.manifest.json` | VM ID, границы, количество событий, состояние и потери |
| `/var/log/incidentsim/sessions/ID/llm.json` | Компактные действия; этот файл отправлять модели |
| `/var/log/incidentsim/sessions/ID/llm.sources.json` | ID исходных событий для каждого действия, SHA256 полного снимка |
| `/var/log/incidentsim/sessions/ID/llm.stats.json` | Объём до/после, число действий, отброшенные детали, опционально токены |
| `/var/log/incidentsim/sessions/ID/session.json` | Состояние конкретного окна |
| `/var/log/incidentsim/capture.json` | Текущее или последнее окно |
| `/var/log/incidentsim/collector-health.json` | Состояние dispatcher-процесса и ошибки преобразования |
| `/etc/incidentsim/audit-context.json` | VM ID и время установки |

JSONL, компактные файлы, manifest и context имеют mode 0600, каталог журналов — 0700.
Исходные audit records сохраняются дополнительно к JSONL.
Ничего не отправляется в LLM или во внешнее хранилище.
Отдельный явный запуск `src/analyze.py` отправляет компактный пакет
выбранному провайдеру. `start`/`stop` и экспорт сетевых вызовов LLM не делают.

## Экспорт и диагностика

```bash
# При необходимости повторно экспортировать закрытое окно:
incident-audit export --session-id attempt-001
# Без --session-id выбирается последнее окно; оно должно быть закрыто.

# Контроль сбора:
incident-audit status

# Дополнительная аннотация внутри активного окна:
incident-audit mark hint_used

# Полный неотфильтрованный диагностический экспорт (не для оценки решения):
incident-audit export --all --output /root/all-audit.jsonl
```

`export` перечитывает raw audit logs через системный libauparse,
объединяет их с JSONL и Bash-событиями, убирает дубликаты по `event_id`,
сортирует по времени и атомарно публикует снимок. Raw logs сначала замораживаются:
экспорт не читает бесконечно события, порождённые собственной работой.
Операции самого `incident-audit` помечены `origin=instrumentation` и исключены
из снимка; для их включения есть `--include-instrumentation`.
В каждой записи есть `capture_session_id`. В manifest находятся
`capture.start_boundary` и `capture.stop_boundary`. Обычный экспорт исключает
подготовку и проверку по этим границам; `--all` намеренно снимает ограничение.
Вызовы start/stop должны добавить внешние системы. Автоматической привязки
к Telegram-боту или `incidentctl verify` утилита не устанавливает.
Старые общие `events.jsonl` и `actions.jsonl` от предыдущей версии сохранены;
внешним системам следует использовать пути, возвращённые stop.

Путь можно изменить: `incident-audit export --output /root/session-actions.jsonl`.
Для обычного анализа используйте компактный `llm.json`; JSONL и manifest нужны
для детального расследования. Поля команд и файлов — недоверенные данные.
Аргументы могут содержать секреты: перед отправкой внешнему провайдеру их
следует очистить.

Пример сокращённого события:

```json
{"schema_version":1,"event_id":"vm:audit:1794398701.123:42","timestamp":"2026-11-11T12:05:01.123+00:00","vm_id":"vm","source":"auditd","kind":"exec","actor":{"login_uid":0,"session_id":3},"process":{"pid":123,"ppid":100,"executable":"/usr/bin/curl","cwd":"/root","argv":["curl","http://localhost/"]},"syscall":"execve","syscall_success":true,"syscall_return":0}
```

`syscall_return` относится к системному вызову. Успешный execve не означает,
что программа позже завершилась успешно. Настоящий результат интерактивной
команды находится в Bash-событии `command_finish.exit_status`;
его `command_id` связывает start и finish. Для pipeline это статус Bash `$?`,
не отдельный статус каждого процесса.

## Ограничения и хранение

- Вывод команд, содержимое файлов, нажатия внутри vim/top и полный сетевой
  трафик не записываются. Открытие файла на запись не является diff.
  `openat2` логируется без фильтра по flags, поэтому может означать чтение.
- Команды других shell и shell-скриптов отражаются через syscall-события;
  полные введённые строки и exit status дополнительно доступны только для
  интерактивного root Bash с включённым hook.
- Root может менять и отключать эту телеметрию. Это материал для учебного
  разбора, не защищённый от участника аудит.
- Raw logs: до 8 файлов по 16 MiB. JSONL каждого окна: до 4 файлов по 16 MiB.
  Старые ротации перезаписываются; бессрочное хранение всех действий не обещается.
  Для длинных или очень активных сессий заранее увеличьте лимиты хранения.
- Промежуточный events.jsonl нужен сборщику: при обработке очереди в нём могут
  оказаться кандидаты за концом окна. Компактный `llm.json` строится из
  actions.jsonl, отфильтрованного по обеим подтверждённым границам.
- Обычный экспорт работает с закрытым окном. Последующие действия пользователя
  и валидатора в этот снимок не добавляются.
- Учебная запись начинается по start; подготовка до него остаётся только
  в системном raw audit-журнале.
  Счётчик потерь находится в manifest как `audit.lost`; не сбрасывайте его.

## Проверка после установки

На целевой машине с установленными пакетами:

```bash
python3 -B -m unittest discover -s tests -t . -v
sudo python3 scripts/verify.py
```

Установщик ставит пакеты, сохраняет прежние конфигурации с суффиксом
`.before-incidentsim`, добавляет правила и dispatcher, включает auditd при
загрузке. `--skip-packages` нужен, если пакеты уже установлены.
VM не перезагружается, пользовательский терминал и бот не перезапускаются.

Установка по SSH от root и от обычного пользователя через sudo проверена на
Ubuntu 24.04. Автоматически созданный ID и журналы сохраняются.
Для сбора и компактного экспорта предусмотрены автоматические тесты и интеграционная
проверка: внешняя команда с Unicode/переносом строки, login UID при sudo,
изменения файлов, Bash builtins, ошибочная команда, ввод exit, дедупликация,
сортировка, восстановление из raw logs, права 0600, отсутствие событий до start
и после stop, остановка роста учебного журнала, компактный экспорт с проверкой
ошибок, повторных команд и ссылок на исходные события. Проверка verify использует
собственное тестовое окно и отказывается запускаться во время активной записи.
После проверки:
`audit.lost=0`, `collector.conversion_errors=0`.
